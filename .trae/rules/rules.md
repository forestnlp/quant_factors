# 第一部分 开发方法论

## 0. 毛选方法论（工作总纲）

以《实践论》《矛盾论》《论持久战》为指导思想，贯穿所有开发任务：

1. **没有调查就没有发言权** — 动手编码前必先调研现状（读数据、看代码、摸环境），掌握一手资料，不做无根据假设。
2. **抓主要矛盾与主要方面** — 面对复杂任务，先分析哪是主要矛盾、哪是矛盾的主要方面，集中资源优先解决，避免平均用力、胡子眉毛一把抓。
3. **集中优势兵力打歼灭战** — 聚焦单一目标，逐个击破，打一个歼灭一个；不铺开战线、不做半途而废。
4. **实事求是、一切从实际出发** — 方案服从于数据与环境的真实情况，不套模板、不空谈理论。
5. **动态规划与闭环管理** — 制定可验证的阶段性目标，执行中依据反馈动态调整；每个阶段以"实践→认识→再实践"循环闭环，验证通过才进入下一阶段。
6. **具体问题具体分析** — 每个任务结合其上下文判断，不机械照搬规则。

> 总纲：先调研 → 抓主要矛盾 → 聚焦歼灭 → 动态闭环。与下方 1-4 条细则配合使用。

## 1. 先想清楚，再动手写代码

**不臆测、不掩饰困惑、主动摆出取舍。**

- ✅ **把假设明确说出来**，不确定就问。
- ✅ **有多种理解时全部列出**，不静默替用户做选择。
- ✅ **该反驳就反驳**，如果有更简单的做法就讲出来。
- ✅ **不懂就停下来问**，清楚说出哪里不懂。

反面做法：❌ 不做核查就自行假设；❌ 心里困惑却闷头继续干；❌ 有多种理解时静默选一种；❌ 带着疑问继续推进。

## 2. 简单优先

**只写解决问题所需的最少代码，不做任何投机性设计。**

- ✅ 只写解决当前问题所必需的代码；不做需求之外的功能。
- ✅ 不为只用一次的代码做抽象；不添加没人要求的"灵活性"与"可配置性"。
- ✅ 不为不可能发生的场景写异常处理。
- ✅ 如果写了 200 行而其实 50 行够用，就重写。

**资深工程师检验法**：问自己"资深工程师会不会说这搞复杂了"，如果会，就简化。

## 3. 精准改动

**只碰必须碰的地方，只清理自己制造的杂乱。**

- ✅ **只改必要的部分**，聚焦当前任务本身；不顺手"改进"周边代码，注释与格式保持原样。
- ✅ **不去重构没坏的代码**；**沿用现有风格**。
- ✅ **发现死代码要说明**，提出来即可，不擅自动手删。
- ✅ **清理自己的烂摊子**：删除因本次改动而失效的导入、变量、函数。

检验标准：每一行改动都能直接追溯到用户的需求。反面做法：❌ "既然改到这里"式范围蔓延；❌ 重新格式化自己没写过的代码；❌ 按个人偏好重命名。

## 4. 以目标驱动执行

**先定义成功标准，然后循环迭代直到验证通过。**

| 模糊任务 | 可验证目标 |
| -------- | ---------- |
| "加点校验" | "为非法输入写测试，然后让测试通过" |
| "修这个 bug" | "先写一个能复现 bug 的测试，再让它通过" |
| "重构 X" | "重构前后测试都通过" |
| "取这批数据" | "落盘后读回核对覆盖区间、行数、NaN 分布，与预期一致" |

多步骤任务先给出简短计划：`1. [步骤] → 验证：[怎么验]`。
**强的成功标准**能让人独立循环推进；**弱的成功标准**（"让它能跑"）会不断回来找人澄清。

## 5. 踩坑教训（血泪换来的，违反即返工）

1. **落盘 ≠ 可用，必须读回验证。** 写完不核对等于没做；任何数据写入收尾都要跑校验并把范围打印出来。
2. **同一 Bug 不修两遍。** 同类写入只允许一个正确实现；新增写入路径必须对齐既有正确实现并过同一道质量门。
3. **基础设施故障不能记成业务失败。** 连接/超时/认证类异常必须 fail-fast 中止并显式告警，绝不静默写成业务结果，绝不污染后续决策输入。
4. **覆盖范围显式核对。** 取数/入库完成必须打印并核对起止日期、标的数、行数、非 NaN 分布——"跑完了"不等于"跑对了范围"。
5. **并行后台任务要克制。** 需要验证的事项一次只做一件；无人值守下不擅自把任务扩到大规模。
6. **重大发现即时归档（自动执行，不等提醒）。** 对话中产生研究结论、踩坑教训、关键数据/工具事实、路线改判时，本轮收尾前必须写入 PROJECT.md（研究结论/已完成/下一步）；属工程纪律的同步进本节。归档是任务的一部分，不是可选动作。

**有效性自查**：动手前是否先出现澄清问题、diff 是否精准可追溯、是否还在"顺手改进"、是否还有未经读回验证就当作成立的数据结论。

# 第二部分 硬性工程规则

## R1. 代码风格

- **Python**: 遵循 PEP 8，公开 API 使用类型注解与中文 docstring。
- **命名**: 统一 `snake_case`。
- **配置**: 环境变量与路径配置集中在 `.env` / `research/config.py`，不硬编码。

## R2. 测试与验证期望

- 新功能需有可验证的成功标准（见方法论第 4 条）。
- 使用 pytest 编写测试；外部服务（网络下载、API）进行 mock 或本地化。

## R3. 数据本地化

- 保持数据本地化，一切路径以 `research/config.py` 的 `raw_dir()` / `derived_dir()` 为准，不硬编码。
- 配置尽量使用环境变量。

## R4. 目录规划（二区隔离 + 数据区 + 工具区）

| 目录 | 性质 | 是否入库 | 说明 |
|------|------|---------|------|
| `research/` | **引擎工作区（提炼/验证）** | ✅ 版本控制 | Harness Loop 核心代码，未最终定型 |
| `src/` | **正式区** | ✅ 版本控制 | 经验证、可复用的正式代码，扁平结构 |
| `docs/` | 文档区 | ✅ 版本控制 | 外部接口文档等参考资料（如聚宽 API 文档） |
| `data/` | 数据区 | ❌ gitignore | 原始层 `data/raw/`、派生层 `data/derived/`，不入库 |
| `.tools/` | 工具区 | ❌ gitignore | vendored 第三方工具源码（如 jqcli），以 `pip install -e` 装入 conda `jaycode` 单环境，两步可重建 |

**核心原则**：

1. **不污染正式区** — 引擎代码先写 `research/`，验证通过再提升到 `src/`。
2. **单线递进流动** — `research/`（提炼验证）→ `src/`（正式）。
3. **提升标准** — 逻辑正确且通过验证、可复用、接口与文档清晰、不依赖实验环境。
4. **数据本地化** — 数据保存在本地，不依赖每次联网。
5. **取数完整** — 覆盖**日线与分钟线**两种粒度，满足因子研究与日内策略两类场景。
6. **验证闭环** — 每个脚本自带可验证的成功标准，跑通后再决定是否提升。
7. **产物不外泄** — 所有日志、结果、缓存只写入项目 `data/` 内，不得写项目目录之外。
8. **项目信息零外泄（硬性）** — 本项目的任何代码、文档、配置、数据、凭据、研究结论，一律不得写入、复制到、下载到项目目录树之外的任何位置；也不得粘贴进外部网页、云端环境、第三方服务或对话之外的渠道。工具、虚拟环境、第三方依赖若需落盘，必须置于项目内（如 `.tools/`）并在 `.gitignore` 中忽略。外部服务（如聚宽、AKShare）仅作为**只读取数通道**：取回的数据沉淀进 `data/`，但绝不把本项目的内容反向传给它们（上传到云端执行的脚本必须只含取数逻辑，不含本项目的因子、结论、凭据）。
9. **数据本地化优先，外部平台只做增强件** — 评估引擎依赖的数据必须驻留本地；云端平台只承担"拉取本地无法获得的独有数据"，须低频克制使用，产物一律本地落盘。任何关键路径不得建立在外部平台可用性之上。
10. **原始层不可再生，派生层随时可重建** — `data/raw/` 存放取数原始落盘，长期保留、只追加不覆盖；一切格式化/转换/聚合产物写 `data/derived/`，必须能从 raw 完整重建。
